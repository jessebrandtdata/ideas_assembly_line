# Bill Delay Tracker prototype

See [`../prototype-bill-delay-tracker.md`](../prototype-bill-delay-tracker.md) for what this is and how to run it.

Each Congress has its own folder, `data/<congress>/` (`data/108/` to `data/119/` today). `collect_warehouse.py` → `versions.csv` (with each printing's size: `sections` and `characters` of its parsed text, and `pages` once the warehouse publishes a page count) + `summaries.csv` there (read from the spicy-regs warehouse's current generation, all eight measure types; needs `duckdb`, no API key) → `delays.py` → `stats.json` + `delays.json` (+ `delays.js`, the same document as a script) per Congress, and `data/congresses.json` (+ `.js`), the index the dashboard opens with → `dashboard/`. `congress.py` works out the current Congress from the date, so nothing names a Congress number and the 120th starts its own folder in January 2027 on the next run. Each folder's `warehouse.json` records which generation the warehouse reader used. Only a small dated snapshot is in git (the index, each Congress's `stats.json` and `warehouse.json`); the rest is rebuilt by the commands above, and `.github/workflows/bill-delay-tracker.yml` rebuilds it daily and publishes `build_site.py`'s output to GitHub Pages.
Lag runs from the date printed on the introduced text to the bill's first CRS summary, whatever version it describes: a reader has a summary from the first one CRS publishes, and a bill CRS never summarized as introduced (S. 1869 of the 115th has one summary, at Public Law) is measured to that later one. Both ends are stand-ins; the "Which dates" section lists every candidate and why these were picked. CRS writes summaries for introduced versions only in the 119th Congress, so the page measures the introduced stage, the one stage every Congress has.
`tests/fixture/` runs `delays.py` on a bundled sample with no network.
`dashboard/index.html` is the view of the data. Open it straight from disk, no server needed: browsers block `fetch()` of local files on `file://` pages, so `delays.py` also writes the data as scripts, `data/congresses.js` (the index) and `data/<congress>/delays.js`, and the page loads them with plain `<script>` tags, a Congress's file when it is picked, under a loading banner that counts the files as they arrive (the d3 library and the webfont still come from the network). The Congress picker opens on the newest Congress with an introduced bill, offers all Congresses pooled as its first option (each bill keeps its Congress), then each Congress on its own; when the data in view spans more than one Congress, a by-Congress chart below the histogram sets them side by side. Serving the prototype folder (`python3 -m http.server`, open `/dashboard/`) works too. The later-stage summaries are counted in the caveat at the foot of the page and kept in `delays.csv` under their stage. Page-wide filters sit in the top row: bill type, a printed-date from/to range (two day-level date pickers bounded by the first and last printed date in the data; empty = open side; inclusive), a "Clear date filters" button, and "Bill size in" (characters or sections; pages once the data has it); a monthly stacked-share chart (summarized vs waiting, by month the text was printed; no lag-over-time lines, which right-censoring would make misleading) shades the months the range touches; beneath the histogram are its own controls, a bin-width slider (7 to 90 days) and a checkbox to include bills still waiting as a gold bar beside the bins. The size card and the cumulative size chart count introduced text versions; the "reported by committee" card counts bills with a reported text version, which needs no summary. Two top-10 tables close the page, both following the page filters and ties broken by Congress and bill number: "Longest lags" (summarized records, by lag in days) and "Oldest bills still waiting" (bills with no summary, by days from the printed date to the data's as-of date); each bill is a link to its congress.gov page.

## Size: pages where looked up, characters and sections everywhere (2026-11-09)

Proposal IV.2's first metric is "the total number of pages in the bills processed". The warehouse has no page count. GovInfo does, one API call per printing (`<extent>9 p.</extent>` in the MODS record). `collect_govinfo.py` makes those calls when asked; it is off by default, and in the Pages workflow it runs only when the repository variable `GOVINFO_PAGES` is `true`. Its `govinfo.csv` for the 119th Congress is committed, all 23,215 printings, so the dashboard offers pages there and characters or sections, counted from the parsed text in `bill_sections`, everywhere (about 99.8% of printings from the 110th Congress on, 69% of the 109th's and 11% of the 108th's). A bill without a value for the measure shown is left out of the totals and counted as unmeasured, never shown as zero. When the warehouse publishes a page count on `bill_versions`, `collect_warehouse.py` reads it into the `pages` column and the lookups become unnecessary.

## Summary date: publication, not revision (2026-11-06)

Proposal IV.2 asks for "the time lag between bill text publication and Congress.gov summary availability". The summary end of that lag is the day the summary first became available, and the Congress.gov field for it (`lastSummaryUpdateDate`, the "Which dates" table below) is overwritten whenever CRS revises a summary, so a revised summary overstates its lag.

Civic Tech DC's spicy-regs warehouse (Parquet at `data.spicygov.ai`, pointer `publication.v2.json`, table `bill_publisher_summaries`) reads the same BILLSTATUS source nightly and, since its 2026-11-06 generation, keeps every dated revision of a summary as its own row instead of overwriting. The earliest retained `update_date` for a bill and summary version is therefore the summary's first publication on the publisher's own clock, which is the date the proposal asks for. The one case it cannot recover is a summary revised twice between two nightly runs, which loses its first stamp before capture; that is bounded to a day. Summaries first captured before 2026-11-06 carry only their latest revision. `collect_warehouse.py` writes the earliest retained revision as `last_summary_update_date`, the date `delays.py` measures to, and the latest as `update_date`.

The text start: the warehouse's `bill_versions.version_date` is the date printed on the bill, before the text is readable, and no source states the day the text appeared on Congress.gov. The warehouse's build receipts record when its reader first saw each printing (`observed_at`), but not on the table, and for printings older than the reader it is the backfill date (the 119th Congress's H.R. 1 as reported, printed 2025-05-20, reads 2026-09-26). Publishing `observed_at` on `bill_versions` would give a first-seen date for every printing from then on.

## Which dates

Proposal IV.2 asks for "the time lag between bill text publication and Congress.gov summary availability". No source publishes either event directly, so the prototype picks the nearest field at each end. The candidates, with each source's own definition:

**Start of the lag (when the text became public)**

| Field | Source | The docs say | Used? |
| --- | --- | --- | --- |
| `version_date` / `dateIssued` | the warehouse's `bill_versions`; GovInfo package summary and collection listing | The date on the document | **Yes** (`text_date`). Every Congress has it and it costs no API call. Equals the introduction date for almost every introduced bill; GovInfo posted 119th Congress introduced bills a median 12 days after it, 28 days at the 90th percentile (2026-10-15 run), so lags read that much longer than a reader's wait. |
| `dateIngested` | GovInfo, per-version MODS record | "The date the document was ingested into the GovInfo preservation repository" ([Bills help page](https://www.govinfo.gov/help/bills), search field `ingestdate`) | Used until 2026-11-09, now no. The closest observable to the text going public, but one API call per printing, and for bills printed before GovInfo's predecessor was migrated it is the migration (a 110th Congress introduced bill reads 2010-09-21). |
| `observed_at` | the warehouse's build receipts | when the warehouse's reader first saw the printing | No. Not on the table, and a backfill date for printings older than the reader. |
| `lastModified` | GovInfo, package summary and `lastModifiedStartDate` filter | "the time that this package was added or updated ... not the equivalent to Date Published, Date Issued, or Date Ingested in MODS" ([usgpo/api README](https://github.com/usgpo/api#lastmodifiedstartdatelastmodifiedenddate-usage)) | No. A bulk reprocess in July 2026 reset it for most of the Congress. |
| `textVersions[].date` | Congress.gov API, bill item | "associated with the date of action, not the printing date" ([BillEndpoint.md](https://github.com/LibraryOfCongress/api.congress.gov/blob/main/Documentation/BillEndpoint.md)) | No. Same information as the printed date, and null for some versions (the enrolled hr1, for one). |
| `updateDateIncludingText` | Congress.gov API, bill level | "The date of update on Congress.gov, including if the update was to bill text" | No. One value per bill, overwritten by every later text and metadata update, so it cannot date an individual version. |

**End of the lag (when the summary became available)**

| Field | Source | The docs say | Used? |
| --- | --- | --- | --- |
| earliest retained `update_date` | the warehouse's `bill_publisher_summaries` | one row per dated revision since 2026-11-06 | **Yes** (`summary_date`). The first publication, for summaries captured since 2026-11-06; the latest revision for older ones. |
| `lastSummaryUpdateDate` | Congress.gov API, summaries | "The date the bill summary was last updated. This date also reflects the date and time when a bill summary is re-published." ([SummariesEndpoint.md](https://github.com/LibraryOfCongress/api.congress.gov/blob/main/Documentation/SummariesEndpoint.md)) | Used before the warehouse; overwritten when CRS revises a summary. |
| `updateDate` | Congress.gov API, summaries | "The date of update on Congress.gov" | No. Moves on any re-save of the record, summary text or not. |
| `actionDate` | Congress.gov API, summaries | "The date of the action associated with the bill summary" | No. It dates the bill action the summary describes (introduction, passage), not the summary; as an end date it would make most introduced lags zero. |

The remaining doubt at both ends comes from reading history off fields that are dated by the publisher or overwritten. A daily record of the first day each printing and each summary is seen removes it; the warehouse's `observed_at` is that record for printings, once it is published. That is the production tool, not this prototype.

## Exports

Each of the five charts has "Download PNG" and "Download SVG" buttons above it, and each of the two tables has a "Download CSV" button in its heading. The files follow the current Congress, bill type and date filters and are named `bill-delay-<figure>-<congress>-<type>[-<from>_<to>]-<as_of>`, for example `bill-delay-histogram-119-all-2026-11-09.png`. The PNG is a fixed-size export: twice the chart's design size (the 920 px wide viewBox plus the title band), the same file whatever the window width. Because an SVG loaded as an image cannot fetch the Google webfont, PNGs use the system fallback font. The CSVs hold every row of the filtered table in its sort order, not only the ten shown (longest lags: all summarized bills; oldest waiting: all bills without a summary), with the printed date, every size measure the data has, the Congress and the congress.gov link.
